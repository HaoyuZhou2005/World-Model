# 26090901 实现审查与下一步计划

> 审核对象：服务器 Agent 在 `/mnt/data4/liboyan/AdaptiveCache/26090901` 的实现总结（2026-09-09）。
>
> 本文的目标不是否定当前 demo。当前 demo 已经把 Wan2.1、cache controller、gate、训练、rollout 串起来，作为工程摸底是有价值的。但其中有几处会直接影响“这是不是一个正确的 AR World Model / cache 方法”以及后续论文结论，必须在继续扩大实验前修正。

---

## 0. 总结结论

当前实现可以定义为：

> **Wan2.1 上的 cache / gate 原型验证器（prototype / simulator）**

目前还不应该定义为：

> **已经正确搭好的 Astra-style AR World Model + 可实际加速的 adaptive cache**

最关键的问题有 7 个：

1. **不能只给原始冻结 Wan2.1 加 temporal causal mask，就把它当成训练好的 AR World Model。** 推荐直接用 Astra 已发布的 Wan2.1-based AR checkpoint 做 baseline。
2. **逐帧 `T=1` VAE encode 是当前最大结构问题之一。** Wan2.1 使用 causal 3D VAE，并且时间压缩比是 4。逐帧编码会改变 latent 的时间分布，和 Wan2.1/Astra 的训练输入不一致。
3. **当前代码混在了一起的其实是两种 cache：历史窗口重叠的“精确复用”和新 observation 与上一 observation 的“近似复用”。** 后面必须拆开。
4. **cache 必须和 `layer + denoising timestep + latent time + spatial position` 对齐。** 只按空间 token 或相邻窗口下标对齐不够。
5. **现在是整层算完再 fusion，所以没有真正省算力。** 这可以用于训练 gate 的 proxy，但不能当作最终推理实现。
6. **当前 `no_grad` 训练描述很可能切断了 future loss 到早期 gate 的梯度。** 需要做梯度路径检查。
7. **当前 rollout 的主要像素指标是相对“输入最后一帧”而不是 ground-truth future。** 这个指标不能评价预测质量，也会偏向静态/复用更多的方法。

在这些问题修正前，不建议继续增加训练 step，也不建议根据现有 PSNR/SSIM 判断 adaptive cache 是否有效。

# 1. 当前已经做对的部分

下面这些设计可以保留。

## 1.1 Wrapper 而不是直接改 Wan2.1 官方源码

当前把官方 Wan2.1 放在 `third_party/Wan2.1`，通过 wrapper 控制 block forward，这个方向是对的。

这样后续可以分别保留：

- 原始 Wan2.1 baseline；
- Astra AR baseline；
- cache 版本；
- 不同 gate / cache ablation。

不要为了 cache 直接大范围修改第三方源码。

## 1.2 Frame gate + Token gate 的分层设计

“先做便宜的粗筛，再做 token 级细筛”仍然是合理的工程设计。

但 frame gate 不能成为最终性能的主要决定因素。现在 horizon=5 时几乎全部触发 full recompute，说明 `MAE > 0.08` 这个规则已经把 token gate 架空了。后面要重新标定。

## 1.3 soft fusion 作为训练 proxy

当前：

```python
h = g * h_fresh + (1 - g) * h_stale
```

作为**可微分的 cache simulator**是合理的。

需要注意：它是训练 proxy，不等于最终真正省 FLOPs 的实现。

## 1.4 Full / Fixed / Random / Adaptive 四组 baseline

这四组可以继续保留，尤其适合早期 sanity check。

后续固定计算预算后再比较：

```text
Full
Fixed-top-k
Random-top-k
Feature-diff-top-k
Adaptive-top-k (Ours)
```

比“不同方法自然产生不同 recompute ratio”更公平。

# 2. 必须优先纠正的问题（P0）

## P0-1：AR World Model baseline 目前不够成立

服务器版本的做法是：

```text
原始 Wan2.1-1.3B
+ temporal causal attention mask
+ 冻结 Wan 参数
= AR World Model
```

这个等式不能直接成立。

[Astra README](https://github.com/EternalEvan/Astra) 明确写的是：Astra 基于 Wan2.1-1.3B，使用 **autoregressive diffusion transformer with temporal causal attention**，并提供了额外训练后的 Astra checkpoint。也就是说，Astra 的 AR 能力不是“给原始 Wan 权重临时套一个 causal mask”得到的，而是模型结构与训练共同得到的。

### 为什么当前做法有风险

原始 Wan2.1 的权重是在它原来的 attention / generation setting 下学习的。直接改变 attention 可见范围，会改变每层 hidden state 的统计分布。

冻结权重后没有任何 adaptation，模型虽然能 forward，但“能跑”不代表“已经成为可靠 AR WM”。

这也可能解释当前 full rollout 本身质量不高。

### 推荐修改

**优先路线：直接把 Astra released checkpoint 作为 AR WM baseline。**

也就是：

```text
Wan2.1-1.3B backbone
        +
Astra released AR checkpoint / inference implementation
        ↓
可靠的 AR World Model baseline
        ↓
再研究 cache
```

Astra 已经提供 inference 代码和 checkpoint。这条路线比自己把 Wan2.1 改成 causal 后再重新训练省很多时间，也更容易保证研究问题聚焦在 cache。

如果后面一定要“从纯 Wan2.1 自己训练成 AR WM”，应该单独作为 Stage A：先完成 causal AR fine-tuning，确认 no-cache 模型质量，再开始 cache。不要同时训练 AR 化和 cache gate。

## P0-2：不要逐帧 `T=1` VAE encode

服务器版本当前：

```text
每帧单独用 Wan VAE encode
T=1 -> latent T=1
再把多个 latent 沿时间拼起来
```

这样做的动机是方便 token 一一对齐，但会破坏 Wan2.1 的原生时间编码方式。

Wan2.1 官方配置中：

```text
vae_stride = (4, 8, 8)
patch_size = (1, 2, 2)
```

Wan2.1 官方 `wan/modules/vae.py` 里的 encode 也不是逐帧独立编码。它使用 causal 3D convolution，并按时间：

```text
第一段 1 帧
之后每段 4 帧
```

进行 causal streaming encode。

参考：

- [Wan2.1 1.3B config](https://github.com/Wan-Video/Wan2.1/blob/main/wan/configs/wan_t2v_1_3B.py)
- [Wan2.1 VAE](https://github.com/Wan-Video/Wan2.1/blob/main/wan/modules/vae.py)

Astra 的训练代码同样显式使用：

```python
time_compression_ratio = 4
```

### 当前做法的问题

原始视频：

```text
frame 0,1,2,3,4,...
```

不能简单认为：

```text
每个 raw frame == 一个独立 Wan latent time token
```

逐帧 `T=1` encode 后拼接，得到的是 Wan DiT 在预训练时没有见过的 temporal latent distribution。

### 必须改成

保留 Wan/Astra 原生 VAE temporal encoding：

```text
raw video clip
   ↓
Wan causal 3D VAE
   ↓
latent chunks / latent time positions
   ↓
DiT tokens
```

后续 cache 的时间对齐单位应该主要是：

> **latent temporal position / chunk**

而不是 raw RGB frame。

### 必须增加一个单元测试

```text
同一段视频：
A. 官方 Wan VAE 一次/官方 streaming encode
B. 我们自己的 data pipeline

检查 latent shape 和数值是否一致/接近。
```

禁止继续使用“逐 RGB 帧 T=1 encode 后拼起来”的版本作为正式实验。

## P0-3：把两种 cache 明确拆开

当前实现把下面两件事混在了一起：

### A. 历史上下文重叠（History Cache）

例如：

```text
previous window: [t, t+1, t+2, t+3]
current  window: [t+1, t+2, t+3, t+4]
```

`t+1,t+2,t+3` 是**同一个历史内容再次出现**。

这是“精确重复计算”。

### B. 相邻 observation 的视觉冗余（Observation Reuse）

`t+4` 是新 observation。

如果它和 `t+3` 很像，可以尝试：

```text
new token(t+4)
≈ cached token(t+3)
```

这是**近似复用**，才需要 learned gate 判断是否安全。

### 当前代码的问题

目前写的是：

```text
当前帧 0..T-2 <- 上一窗口帧 1..T-1
当前最后一帧 <- 上一窗口最后一帧同位置 token
```

前半段是 exact overlap cache。

最后一段则突然变成 adjacent-frame approximate reuse。

两类 cache 的理论依据完全不同，不应该放在同一个映射逻辑里。

### 建议把 “Dual-Horizon” 正式定义为

#### Long / History Horizon

```text
历史 context 重复
→ deterministic reuse
→ 不需要 gate
```

#### Short / Observation Horizon

```text
新 observation vs 最近 observation
→ approximate reuse
→ frame gate + token gate
```

这样项目的科学问题会更清楚：

> 对完全重复的历史计算做确定性缓存；对相邻 observation 中的视觉冗余，学习 future-safe 的近似复用策略。

建议后续把代码也分成：

```text
models/cache/
├── history_cache.py
├── observation_cache.py
├── token_gate.py
└── controller.py
```

## P0-4：cache key 必须包含 denoising timestep

当前总结没有看到 cache 对 diffusion/flow timestep 做严格区分。

这是危险的。

Wan/Astra 的 DiT hidden state 不只是：

```text
h = f(image token)
```

更准确是：

```text
h_l = f_l(x_t, diffusion_timestep, text/action condition, context)
```

同一个空间位置，在不同 denoising timestep 下 hidden state 不一样。

所以 cache 不能只用：

```text
(frame, spatial_token)
```

作为 key。

### 推荐 CacheKey

至少包含：

```python
CacheKey(
    layer_id,
    denoise_step_or_timestep,
    latent_time_index,
    spatial_index,
    branch_id,          # 如果有 CFG / condition branch
)
```

如果 Astra rollout 中 history latent 是 clean/noise-augmented memory，还要把“history / target token type”区分开。

### 必须做的 sanity test

同一个 sample：

```text
Full causal forward
vs
只对 exact history 做 cache reuse
```

在同 timestep、同条件下，两者输出应该非常接近。

如果 exact history cache 都对不上，就不要开始 approximate token reuse。

## P0-5：Gate 现在放在“算完 block 以后”，不能产生真实加速

当前流程：

```text
完整 Wan block forward
      ↓
h_fresh 已经全部算完
      ↓
gate
      ↓
fusion with stale
```

这个版本的功能是：

> 模拟“如果某些 token 没算，会发生什么”。

它不是：

> 真正跳过这些 token 的计算。

所以当前 `recompute_ratio` 不能直接当成真实 speedup。

而且 attention FLOPs 也不是简单与 token 数线性对应，因此“50% token recompute = 50% FLOPs”也不能直接成立。

### 推荐分两步实现

#### V1：Cache Simulator

保留现在的完整 block + fusion。

目标只有：

```text
验证 gate 是否能学会 future-safe reuse
```

所有论文图中必须标成：

```text
simulated recompute ratio / proxy budget
```

不要报真实加速倍数。

#### V2：True Token Skip

真正的 gate 必须在 expensive computation 之前决定 active token。

建议每层：

```text
pre-block hidden x_l
+ stale cached feature / stale KV
+ timestep embedding
        ↓
cheap gate MLP
        ↓
active token indices
        ↓
只对 active token 做 fresh projection / FFN
```

attention 需要单独设计：

- active token：fresh Q/K/V；
- reused token：使用 cached K/V；
- 只对 active query 计算 attention；
- reused output 直接拿 stale block output；
- FFN 只对 active token 执行。

初版可以用 gather/scatter 实现，哪怕 wall-clock 暂时不快，也要先保证计算语义是对的。

之后再考虑 Triton / fused kernel。

## P0-6：检查 gate 的梯度路径

当前训练说明：

```text
block computation no_grad
只有 fusion 进图
每层用 hidden L1 给 gate 信号
```

这里要非常小心。

如果：

```python
with torch.no_grad():
    h_fresh = block(h)
```

随后下一层也在 `no_grad` 中消费上一层 fused `h`，那么跨层计算图会被切断。

这种情况下：

- 每层 local hidden loss 可以训练对应 gate；
- 最终 future loss 很可能只能训练非常靠后的 gate；
- 早期 gate 并没有真正通过 long-horizon/future loss 学习。

这样会偏离 proposal 里的“future-aware”。

### 下一步必须先做 gradient audit

训练一个 batch 后打印：

```python
for layer_id, gate in gates.items():
    print(layer_id, gate.mlp[0].weight.grad.norm())
```

要求：

```text
所有希望被 future loss 训练的层
都有非零 grad
```

并单独做两次 backward：

```text
A. only L_future
B. only L_hidden
```

看每层 gate 到底由哪个 loss 在训练。

### 两条可选路线

#### 路线 A：真正 end-to-end future-aware

Wan 参数：

```python
requires_grad_(False)
```

但不要对 forward 全部 `torch.no_grad()`。

这样不会计算 Wan 参数梯度，但仍保留 hidden 对 gate/input 的梯度图。

显存不够就：

- gradient checkpointing；
- 降低 resolution/context；
- 只在部分 block 先训练 gate；
- bf16。

#### 路线 B：local surrogate

如果显存确实不允许 end-to-end，就明确写成：

```text
local teacher-distillation gate
```

用每层 teacher hidden / output discrepancy 训练。

此时不要把它描述成“future rollout loss 直接监督所有 gate”。

## P0-7：当前 rollout 质量指标要全部重算

服务器总结里 horizon=1 的表写的是：

> 相对输入最后一帧的像素质量

这不是 future prediction accuracy。

例如模型直接复制最后一帧：

```text
prediction = input_last_frame
```

那么它会在这个指标上非常占便宜。

这很可能解释为什么当前 Adaptive / Random 的 PSNR 反而比 Full 高。

这个结果不能用于证明 adaptive cache 更好。

### 正确评估

必须使用：

```text
predicted frame t+k
vs
ground-truth frame t+k
```

所以 dataset 不能只准备：

```text
context=4 + future=1 + shift frame
```

要直接生成支持：

```text
context C
future H >= 20
```

的 clip。

例如：

```text
C = 16 raw frames
H = 20 raw frames
```

具体 raw-frame 数量要和 Wan/Astra VAE 时间压缩及 Astra target chunk 定义对齐。

### 建议报告

```text
H=1 / 5 / 10 / 20

L1 / PSNR / SSIM / LPIPS
+ FVD（数据规模足够后）
```

还要加：

```text
Full-vs-Cached prediction discrepancy
```

因为 cache 论文最直接的问题是：

> 相同 WM 下，cache 让输出偏离 full baseline 多少？

## P1-3：frame gate 的 `0.08` 阈值没有依据

当前：

```python
score = mean(abs(current - previous))
if score > 0.08:
    full_recompute
```

这个阈值是手工给的，而且已经在 horizon=5 时导致几乎所有样本 full recompute。

### 应改为 calibration

在 validation set 上统计：

```text
frame change score distribution
future error after reuse
```

再选 threshold。

至少画：

```text
x: frame MAE / latent delta
 y: reuse-induced future error
```

如果二者相关性弱，就说明 pixel MAE 不适合做 frame gate。

更推荐同时测试：

```text
pixel MAE
latent L1/L2
pre-DiT feature cosine distance
```

frame gate 只应该做“明显变化时的 cheap fail-safe”，不应该让大多数 rollout 都退化成 full。

## P1-4：不要继续固定 hard threshold=0.5

训练日志里：

```text
step 60: mean(g) ≈ 0.004
```

但 validation adaptive：

```text
recompute_ratio ≈ 0.935
```

这两个数字需要先解释清楚。

可能来源包括：

- frame gate 大量触发 full；
- train/val distribution shift；
- soft gate 与 hard 0.5 不匹配；
- 统计的是不同层/不同条件下的 gate；
- controller 对 frame gate 和 token gate 的 ratio 混在一起。

### 必须把日志拆开

每次 eval 输出：

```text
frame_full_ratio
conditional_token_recompute_ratio
final_total_recompute_ratio
layerwise_gate_mean
layerwise_hard_recompute_ratio
p10/p50/p90 gate score
```

### 推荐改成固定 budget 的 top-k

例如目标重算预算 `rho=0.5`：

```python
score = gate(x)
active = topk(score, k=int(rho * N))
```

这样：

- Fixed 50%
- Random 50%
- Ours 50%

都有完全相同的 token budget，比较更公平。

训练可以用：

```text
soft sigmoid + temperature annealing
```

或：

```text
budget loss = (mean(g) - rho)^2
```

后期再切 hard top-k。

## P1-5：重新检查 flow matching 训练定义

当前自己写了：

```python
x_t = (1-t) * x_1 + t * eps
t ~ U(0.15, 0.85)
```

以及 future velocity target。

这里不能只凭常见 flow matching 公式直接实现。

必须和：

- Wan2.1 scheduler；
- Astra training/inference timestep convention；
- velocity 的正负方向；
- timestep scaling；

完全对齐。

否则 teacher/full 本身就在一个非原训练分布上运行。

下一版应尽量复用 Astra/Wan 已有 scheduler 与 training utilities，不自己重写一套 timestep 逻辑。

## Stage D：再做 Observation Adaptive Cache

这是论文真正的新东西。

### D1. Gate 输入不要只写成一个模糊的 `hidden state`

建议明确为 cheap features：

```text
current pre-block hidden x_l
stale cached hidden h_stale_l
|x_l - stale_input_l|
cosine(x_l, stale_input_l)
timestep embedding
layer embedding
```

初版可以：

```python
gate_input = cat([
    x_current,
    x_current - x_stale,
])
```

再经过小 MLP。

关键原则：

> gate 的输入必须在决定是否 fresh compute 之前就能拿到。

否则没有加速意义。

### D2. 先保持 simulator 训练

可以继续：

```text
full fresh block
+ stale cache
+ soft fusion
```

但明确命名：

```text
cache_simulator
```

### D3. Fix gradient graph

先跑 gradient audit，再开始正式 gate training。

### D4. 固定预算训练和评估

至少测试：

```text
rho = 0.25 / 0.50 / 0.75
```

得到 quality-compute curve。

论文真正需要的不是一个单点：

```text
50% recompute
```

而是：

```text
quality vs compute budget Pareto curve
```

## Stage E：实现真正 token skipping

这个阶段再追求速度。

### E1. 先对 FFN 做 active-token gather/scatter

FFN 是逐 token 的，最容易真实跳过。

```python
active_x = x[:, active_idx]
active_y = ffn(active_x)
y = stale_y.clone()
y[:, active_idx] = active_y
```

先验证数值逻辑。

### E2. 再改 attention

目标是：

```text
active query fresh compute
reused token cached KV
```

而不是整张 attention 都算完。

### E3. 最后才做 kernel optimization

PyTorch gather/scatter 版本可能因为 kernel launch / irregular indexing 暂时不比 dense 快。

这不代表方法无效。

工程路线：

```text
correct sparse semantics
→ theoretical FLOPs
→ profiler
→ Triton/fused kernel
→ wall-clock speedup
```

# 9. 当前最重要的研究表述

项目后续建议统一成下面这套逻辑。

## 问题

AR World Model 有两类重复计算：

```text
A. rollout 中反复出现的历史 context
B. 相邻 observation 中大量静态/低变化视觉区域
```

## 方法

```text
History horizon:
完全重复历史 → deterministic cache

Observation horizon:
新 observation → frame-level cheap screening
                  → token-level future-aware gate
                  → selective recomputation
```

## 研究核心

真正值得证明的不是：

> 画面变化小的时候可以 cache。

而是：

> 在相同计算预算下，一个由 future prediction signal 学到的 gate，能比 random、fixed 和纯视觉差分策略更好地保持 long-horizon rollout stability。

这才是后续实验设计应该围绕的主问题。
